# U1→U4 烧录测试 — 问题记录 & 待处理

> 日期: 2026-08-07
> 目标: 打通 U1(治具主控) → U4(测径板 STM32G031G8U6) 的 ISP 烧录链路
> 结论: **烧录链路已打通 (PROGRAM 返回 0x00), 但使用 16 字节测试固件, 真实固件/SN/双槽待推进**

---

## 一、任务背景

U1 是烧录治具, 通过 USART2 (PA2/PA3, 115200, 8E1) + BOOT0(PA8) + NRST(PB15) 控制 U4 进入 STM32 系统 bootloader, 用 AN2606 ISP 协议烧录 U4 固件。固件先通过 PC 上传到 U1 的 SPI Flash (GD25Q128), 再由 U1 读出经 ISP 写入 U4。

---

## 二、问题清单 (按调试顺序)

### 问题 1: SPI Flash slot0 (0x10000) 写入掉电丢失

**现象**: 上传固件到 slot0 后立即读回正常, 但断电重启后变 0x00。slot1 (0x20000) 历次重启都在。

**排查**:
- 换地址测试: 0x00000 / 0x10000 都丢, 0x20000 持久
- 等 1 分钟再写: 无效
- 软件复位 (0x66+0x99): 无效
- 降 SPI 时钟 18→9MHz: 无效
- 去 SoftwareReset: 无效
- 第 1 次/第 2 次写入: 都丢

**根因 (2026-08-10 推翻)**: ~~GD25Q128 slot0 区域硬件损坏~~ **错误**。

**实测反转**: FlashMap 诊断 (0x0028) 对 14 个地址 (0x00000~0xC0000) 直接 GD25Q 写入 + 30s 保持 + **掉电重启后只读验证** → **全部 0x03 完好**, 含 0x00000/0x10000(slot0)。芯片无任何坏区。

**重新结论**: 原"slot0 掉电丢失"**不是硬件缺陷**, 是旧双槽上传流程/测试方法的问题 (已无法复现)。当前驱动 + 恢复后的双槽逻辑实测: 上传双槽 → 掉电重启 → QUERY_FW_VER 版本仍在 → PROGRAM 双段烧录 ACK 0x00。

**处理**: 恢复双槽 (2026-08-10):
- `fw_upload.c`: FW_START `base = upload_slot? slot1 : slot0`, FW_END `cur_slot = upload_slot`
- `app.c`: PROGRAM 读双槽头部双校验; case 2 烧 Bootloader(slot0), case 3 (放开 #if 0) 烧 App(slot1, 目标 8 字节对齐); case 10 段切换
- `app.h`: FW_SLOT0_BASE=0x10000 恢复启用

**待办**: 原"换 GD25Q128"结论作废, **无需换芯片**。

### 问题 2: U4_ScanReport 吃掉 ISP 的 0x79 响应

**现象**: U4 回了 0x79 (CH340 监听确认), 但 U1 握手失败 (0x04)。

**排查**: CH340 监听 U4 PA2 收到 0x79, 说明 U4 正常响应。U1 收不到 → 接收链路问题。

**根因**: U1 的 `U4_ScanReport` 在主循环里持续扫描 UART2 FIFO (用于 U4 运行时 0x30 报文), **把 ISP 的 0x79 响应当作无用数据吃掉并丢弃**。

**处理**: **ISP 烧录期间暂停 U4_ScanReport**。

**代码位置**:
- `protocol_u4.c`: 新增 `u4_scan_pause` + `U4_ScanPause()`, `U4_ScanReport` 暂停时跳过
- `protocol_u4.h`: 声明 `U4_ScanPause`
- `app.c`: PROGRAM case 0 设 `U4_ScanPause(1)`, case 1/10 失败和 case 4 完成设 `(0)`

### 问题 3: USART2 DMA 接收启动后停止, 0x79 进不了 FIFO

**现象**: U4_ScanPause 后仍 0x04。UART2_DIAG 诊断显示: SR 的 RXNE=1 (收到 0x79), 但 NDTR 没变 (DMA 没传输), CR3 DMAR=0, DMA EN=0, RxState=READY。

**排查**: 加诊断命令 (0x0027) 读 USART2 SR/CR1/CR3 + DMA NDTR/CCR + FIFO 状态。发现 DMA 启动成功 (u4_dma_start_ok=1) 但运行时被禁用 (EN=0, DMAR=0), SR 有 FE/ORE 错误。

**根因**: **USART2 的 DMA 接收在传输 1 次后停止** (帧错误/溢出触发 HAL 停止接收), 0x79 进不了 FIFO。具体触发原因未完全确定 (9E1 模式 + DMA 的兼容性问题)。

**处理**: **ISP 期间改用阻塞收发 (HAL_UART_Receive), 绕开 DMA**。

**代码位置**:
- `isp_programmer.c`:
  - ISP_Connect 开头 `HAL_UART_DMAStop` + 清错误标志
  - ISP_WaitForACK 用 `HAL_UART_Receive` (阻塞)
  - ISP_ReadMemory 读数据用 `HAL_UART_Receive`
  - ISP_Go 结束恢复 `HAL_UART_Receive_DMA`
  - ISP_SendCommand 加清接收残留
- `bsp_uart.c`: u4_dma_buf 加 `__ALIGN_BEGIN` (8 字节对齐), 新增 `u4_dma_start_ok` 诊断
- `app.c`: 诊断命令 0x0027 (UART2_DIAG)

**遗留**: USART2 运行时 DMA 接收仍可能有问题 (U4 运行时 0x30 报文靠它)。**待验证**: 恢复 DMA 接收后 U4 运行时通信是否正常。

### 问题 4: G031 擦除格式错误, 擦除参数无响应

**现象**: 握手 (0x7F→0x79) 和擦除命令 (0x44→0x79) 成功, 但擦除参数后 U4 无响应 (加长超时到 10s 仍无响应)。

**排查**: 用 PC USB-TTL 直连 U4 bootloader 手动测:
- 发 `44 BB` → 收 0x79 (擦除命令 ACK)
- 发 `00 FF FF 00` (带 N-1) → 无响应
- 发 `FF FF 00` (F1 格式, 无 N-1) → 收 0x79 (擦除成功!)

**根因**: **G031 的 bootloader 擦除格式是 F1 格式 `0x44 + 0xFF 0xFF 0x00`**, 不是 agent 推测的带 N-1 格式。

**处理**: ISP_MassErase 改为 `erase_packet[3] = {0xFF, 0xFF, 0x00}`。

**代码位置**: `isp_programmer.c` ISP_MassErase

---

### 问题 5: 写内存命令 0x31 被 NACK (0x1F)

**现象**: 擦除成功后, 写内存 0x31 被 U4 NACK。PC USB-TTL 直连确认。

**根因** (agent 分析): **G0 bootloader 要求写内存的数据长度 N 必须 4/8 字节对齐, 地址 8 字节对齐**。当前代码无对齐约束。

**处理**: 
- ISP_WriteMemory 加 8 字节对齐校验 (length & 地址)
- app.c 写循环 chunk 补齐到 8 字节 (不足补 0xFF)

**代码位置**: `isp_programmer.c` ISP_WriteMemory, `app.c` APP_ProgramStep case 10

### 问题 6: 读内存 0x11 缺长度校验字节 → 擦除被 NACK (SN 读 UID 时发现)

**现象** (2026-08-10, 恢复 SN 读 UID 后首次测试): PROGRAM 回 **0x04 (ERR_PROG)**。COM4 监听: `79 79 79` 后延时 ~500ms 出现 `1F`。

**排查**:
- 3 个 0x79 = 握手 (0x7F)、读命令 (0x11)、地址 ACK
- 发长度字节 `0x0B` (N-1=12-1) 后 U4 无数据返回; ~500ms 后 U1 读超时 (ISP_ERR_READ), SN 静默跳过
- U1 随即发擦除命令 `0x44 0xBB`, U4 把 `0x44` 当读命令的校验字节 → 不匹配 → 立刻回 `1F` NACK
- 擦除失败 → PROGRAM 0x04

**根因 1**: **AN3155 规定 Read Memory 的长度字节 N-1 后必须跟校验字节 `(N-1) XOR 0xFF`**。`ISP_ReadMemory` 只发了 `0x0B` 漏发 `0xF4`, 导致 bootloader 等待校验 → 超时 → 后续命令被误判为校验字节而 NACK。

**根因 2 (重测后)**: 补发校验字节后 UID 读取成功 (实测: 3 ACK + 12B UID), 但 `ISP_ReadMemory` 读完数据后等尾随 ACK (100ms) 超时 → 返回 ISP_ERR_READ → **SN 帧不发**。G031 bootloader **读内存无尾随 ACK** (字节计数: 3 ACK + 12B UID + 7 烧录 ACK = 23B 正好)。

**处理**:
- ① 长度字节后补发 `(N-1)^0xFF` (isp_programmer.c ISP_ReadMemory)
- ② 读完数据后改短超时 (20ms) 等尾随 ACK: 有则消费, 无则视为成功 (数据已读全)
- ③ 验证: SN 帧 `A5 5B 00 24 00 00 00 10 01 [UID 12B][校验][00 00] CRC=38 60` CRC 计算匹配 ✓; UID = `79 AE 00 5A 00 07 50 52 47 55 39 33` (含 ASCII "PRGU93"); XOR 校验 `0x90` 手算匹配 ✓; PROGRAM ACK `00 B2 9A` CRC 匹配 ✓

**代码位置**: `isp_programmer.c` ISP_ReadMemory (补校验字节 + 尾随 ACK 容忍)
**状态**: ✅ **已修复并实测验证通过 (2026-08-10)**

## 六、关键协议帧参考

```
握手:    7F                      → U4 回 79
擦除:    44 BB                   → U4 回 79
          FF FF 00               → U4 回 79 (擦除成功)
写内存:  31 CE                   → U4 回 79
          08 00 00 00 08         (地址 0x08000000 + 校验)
          0F + 数据16B + 校验     (N-1=0x0F, N=16 需 8 对齐)
读内存:  11 EE                   → U4 回 79          (SN 读 UID 用)
          1F FF 75 90 05         (地址 0x1FFF7590 + XOR校验)
          0B F4                  (N-1=0x0B, 校验=(N-1)^0xFF) → U4 回 12B 数据, 无尾随 ACK
Go:      21 DE                   → U4 回 79
          08 00 00 00 08         (0x08000000 + 校验)
```

> ⚠️ 读内存 N-1 后**必须**跟校验字节 `(N-1)^0xFF`, 漏发会导致 bootloader 把下一命令当校验而 NACK (问题 6); 读内存**无尾随 ACK** (问题 6 根因 2)。
